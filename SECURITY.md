# Security

## Reporting a vulnerability

Please do not post vulnerability details in a public issue. Use the repository's *Security* tab → *Report a vulnerability* if it is offered; if it is not, open a public issue that says only "security report, please contact me" (no details) and the maintainers will arrange a private channel. Include the version (`turbo --version`), what you did, and what you expected. We aim to acknowledge within a few days.

## Threat model

TurboShift runs as an ordinary user and changes system settings on that user's behalf. The things worth protecting:

1. **No silent privilege escalation.** The app never runs as root. A warning is shown if it is started as root.
2. **A tiny privileged surface.** The only root operation is `write-sysfs`, and the allowlist is a fixed table of anchored path patterns, each with its own value pattern (see `rules` in `internal/privilege/privilege.go`): CPU governor, energy preference and Intel P-state floor/boost, the boost switches, the ACPI platform profile, about twenty-five `vm`/`kernel`/`net` sysctls, per-disk I/O scheduler, read-ahead, request affinity, merging and entropy, THP and its defrag policy, zswap, KSM, PCIe ASPM, USB autosuspend and `usbhid` polling, one Intel GPU clock, PCI runtime power control and the AMD GPU clock level. Patterns contain no wildcard that can match `/`, and numeric settings accept only their valid range (for example swappiness 0-200; three settings whose digits alone could do harm also have numeric ceilings: `min_free_kbytes` 4 GiB, `max_map_count` 2^31-1, `tcp_notsent_lowat` 2^32-1); the first rule, for instance, is `/sys/devices/system/cpu/cpu<N>/cpufreq/scaling_governor` with a value matching `^[a-z0-9_-]{1,32}$`. Requests are validated in the unprivileged process (fail fast, before any prompt) *and again* in the root helper (`turbo __priv`, started via `pkexec <path-to-turbo> __priv <op> <path> <value> [<path> <value> ...]`). The helper takes one or several pairs so all CPU threads or disks change under one prompt; every pair must pass, otherwise nothing is written. Arguments travel as an argv array; no shell is ever involved. The helper refuses to run unless its effective UID is 0, and refuses to write attributes that do not already exist (it never creates files). The unprivileged side only offers the polkit path when the running binary and every parent directory are root-owned, not group/world-writable and not symlinks (otherwise any process of your user could swap the binary that polkit launches as root); run `sudo make install` to satisfy this.
3. **No data loss, no half-applied states.** Changes are journaled before they happen, written atomically with a SHA-256 checksum and `0600` permissions, protected by an exclusive file lock (one transaction at a time), verified after applying, and rolled back automatically on failure. Interrupted transactions are recovered on next start.
4. **Journal integrity.** A corrupted or tampered restore point fails its checksum and is ignored and reported, never acted on. Restore ids are validated against a strict pattern, so path-like ids cannot reach the filesystem.
5. **Journal values are untrusted too.** Values read back from restore points are re-validated (`^[a-z0-9][a-z0-9_-]{0,31}$`) before they reach a command line, so a tampered journal cannot inject options into `powerprofilesctl`/`nmcli`.
6. **Untrusted input.** Benchmark logs are parsed with bounded line lengths and strict row validation. Command output from system tools is parsed defensively; unexpected output is treated as "unknown", not as a trusted value.
7. **No outbound connections** unless the user explicitly consents (see [PRIVACY.md](PRIVACY.md)).

## Out of scope / known limits

- The pkexec path trusts the polkit configuration of the system. `make install` adds an action (`packaging/polkit`) that matches only `<installed turbo> __priv` and lets an active local session keep one authorisation for polkit's usual retention time (about five minutes), so a preset asks once; remote and inactive sessions are always asked. Remove the file to get the stricter default (ask every time). The XML is checked by a unit test and by `xmllint`, but it has **not** been exercised against a live polkit daemon.
- A local attacker who already controls your user account can edit your own state files; the checksum detects accidents and casual tampering, not a determined same-user attacker.
- The privileged flow was verified with a fake executor, unit tests of the allowlist and of the binary-ownership check, and by running the helper's refusals in containers, **not** with a real polkit prompt (see the README's status section).
- Dependencies are checked with `govulncheck` (clean at release) and are all MIT/BSD-3; see [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).
